# 创作中心切换会话仍卡顿

## 需求与复现操作

- 时间：2026-11-06；调查基线 `9459e7ec9f21015597cfa7a380199737d47078ea`，Windows Desktop 2.2.49。
- 现场：用户在创作中心的本机三个会话间反复切换，明显慢于 IM；截图中历史包含长正文、表格和工具调用。当前截图对应的进程/安装包身份尚未读取，不使用本机现装旧进程代替。
- 操作：进入创作中心，连续点击 A → B → C → A；覆盖首次打开、已访问会话重返、后台任务持续更新和较长历史。
- 预期：选中与首屏及时响应，重复切换不反复做与可见内容无关的工作；消息按需加载，草稿、工具操作、会话隔离及加载更早消息的阅读锚点保持正确。
- 本地复现使用独立临时 SQLite 数据库和 Fake model，生成长正文/表格/代码/工具结果；不读取用户聊天、不请求供应商、不停止或替换用户正在运行的程序。

## 调查观察

- `AgentChatPanel::reloadFromStore` 确实已按索引读取最新 40 条消息，但一条 assistant 消息可包含许多文本片段及工具调用；消息数分页没有限制一次 GUI 重建的工作量。
- 每次 `openSession` 都清空整个 MarkdownView，重新生成正文布局与工具控件；没有重用已访问会话的渲染状态。
- 普通会话选择也发出 `sessionListChanged`，上层同步重建整个本机/远端会话侧栏。
- `AgentController::onEventQueued(MessagePartUpdated)` 仍存在每次工具状态事件读取该会话全部历史的路径，后台任务也在 GUI 线程上执行它；需改为现有单消息查询并回归。

## 最小复现与基线

`AgentPanelSessionTest::sessionSwitchRetainsUnchangedRenderedMessages` 使用两个临时 SQLite 会话，每个 80 条历史，首屏读取最后 40 条；每条 assistant 含格式化正文、表格、代码块和 12 次已完成工具调用。先 A → B → A，保留原消息引用控件的 `QPointer`，验证切回后该控件仍在使用。

- 基线实际 GUI：读取 40 条 **3.646 ms**；首次 `openSession` **849.953 ms**，包含事件处理/首帧 **916.618 ms**；重返 **711.488 ms**，包含首帧 **716.466 ms**。
- 基线回归失败：原引用控件已被隐藏并安排销毁，重返不是同一渲染对象。日志：`.cache/desktop-player-style-20261105/session-switch-red-cdb.log`。
- 实际窗口为新构建的 QtTest，构建先完成 `maichat` 的正常部署/95 项依赖检查；不是用户已登录 App 的历史或运行进程。
- 控制器另用真实 SQLite ROW trace 记录 GUI 事件读取量。挂接、数据库路径、单消息读取三项自检通过后，旧实现每个片段事件读 **32 条 message**，预期只读所属 **1 条 message + 3 个 parts**，有效 RED 日志 `session-event-owner-calibrated-red-cdb.log`。此前一个未匹配 Windows 路径的观测脚本计数 0，不作为性能证据。

## 选定方案与执行顺序

用户明确要求不要每次销毁全部重建，因此采用有限会话页面复用；不通过删除历史或改变模型上下文来提速。

1. **事件读取**：控制器通过现有 `getMessage(sessionId,messageId)` 点查事件所属消息，保持正文/推理区分和工具状态通知。
2. **渲染状态**：同一个 MarkdownView 支持保存和恢复页面，包括原始控件、解析结果、布局、选区和代码横向偏移；内容、主题或宽度变化时才重排对应文本。隐藏页面不参与当前页事件命中和排版。
3. **会话缓存**：创作中心保留当前页与最近两个非活动页。切回后读取最新一页作权威协调，只更新发生变化的消息；保留草稿、分页索引及原消息控件。淘汰超过上限的最久未使用页。
4. **交互协调**：待回答和审批使用 Core 当前列表；任务在后台完成、历史被清空、会话被删除、工作目录变化等情况不能恢复旧状态。切走页的播放暂停，恢复不自动播放。
5. **回归**：同一富历史用例对比；新增后台消息增量补入、缓存页清空、LRU 淘汰及草稿、后台已回答问题等测试，执行原有 Markdown、Agent 面板/控制器及窗口相关回归。

### iOS 对照的准确范围

核对的是源码，非本机 iOS 实测。iOS `AIAssistantModel.selectConversation` 在后台 actor 读取最近 8 条，读取完成前保留当前画面，完成后无动画替换；相同会话不重新读取。SwiftUI 消息有稳定 ID/Equatable，`ChatView.swift` 共享 `MarkdownRenderCache` 缓存解析和行内样式（256 项/4 MiB），折叠工具详情只在展开时创建。

iOS 没有每个会话整页常驻的缓存，A/B 替换消息数组后原行会退出当前树。因此本次桌面的有限整页复用是针对当前问题的实现，不能声称 iOS 已采用完全相同方案。

## 剩余延迟的二次定位

仅保留页面但把控件移到隐藏 host 的首版，控件保留回归通过，重返仍约 **329–335 ms**。定点日志证明：100 个展示条目、60 个根控件（内部含 240 个工具卡），切走时根控件换父级 **161.350 ms**，恢复换父级 **153.903 ms**；恢复其它排版仅约 1 ms。瓶颈是 Qt 换父级导致的控件子树样式重算。

最终保留原 viewport 父级，对非活动页只隐藏根控件，用 QObject 事件过滤器阻止异步 `show()` 将它们泄漏到当前页；通过 QPointer 释放被淘汰页面。文本布局按内容、样式/主题版本及可用宽度复用；恢复前保留滚动条占位，防止临时多出 8px 宽度把已缓存正文再次重排。

- 同一基准：重返 **19.815 ms**，含绘制 **21.912 ms**；保存根控件 **0.062 ms**，恢复根控件 **0.044 ms**。
- root 独立整套回归重测：重返 **18.751 ms**，含绘制 **21.181 ms**。冷页仍需构建，实测 **709.775 ms**；本次优化针对重复切换，不把首访成本写成已消失。
- 真实 MainWindow + FakeRemoteIMClient + 三个独立本地会话，以鼠标点击侧栏 A → B → C → A：重返点击处理 **20.890 ms**，含首帧 **25.291 ms**。使用正常产品字体与 DPI 配置，截图 `screenshots/session-switch-main-window.png` 已查看。
- 去掉“选择会话也发目录变更通知”后，主窗口初始化必须显式加载一次已有会话目录。真实主窗口用例曾稳定失败在目录没有初始行；补齐初始化 `refresh/setCurrent` 后通过。正常点击继续只更新选中状态。

以上为本机受控富历史数据，不替代用户另一台 Windows 的实际账号验收，不保证所有硬件/历史都达到相同毫秒数。

## 本轮追加的子任务卡片反馈

用户随后要求优化子任务卡片。旧卡片按自然宽度布局且只有一行被截断的摘要；新的实际面板回归观测到相邻卡片宽度 **212 px / 348 px**，统一宽度断言 RED。

选定交互：任务名、状态、摘要分层；使用正文列的统一宽度，紧凑两行摘要，长内容可原位展开并复制保留的进展文本，不新建对话或模型调用。展开/折叠、resize 及真实截图另做回归。

独立审查还发现真实后台状态缺口：子任务权限批准后卡片变为 Running，切离父页后工具完成，返回时原恢复逻辑只刷新仍 waiting 的审批卡。新增 gated 假工具回归确认完成状态仍旧，得到 RED。恢复时改为对已有审批 owner 点查真实状态，再恢复当前真正 pending 的审批请求。
