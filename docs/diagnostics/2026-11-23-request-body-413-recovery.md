# HTTP 413 请求体超限恢复

2026-11-23。用户会话持续返回 `HTTP 413 ... Maximum size is 52428800 bytes`，正常重发仍被拒绝。此数值为该接收端声明的 50 MiB 请求体上限，不是模型 token 窗口。未读取或导出用户会话数据库，未发真实供应商请求。

## 根因与范围

基线为 `013148365c3c4e9355822a0b859dea6cffff05cb`（尚未发布的 3.2.0 两项跨设备修复候选）。Chat/Responses 原先把 HTTP 413 归为普通 Protocol；Runner 只针对明确的 token 窗口错误做强制压缩，因而相同的大请求会持续失败。

媒体 token 估算不等于图片 Base64 与 JSON 的实际字节数。摘要请求原先也只按 token 分块，不能依赖它解决所有请求体限制。

## 修改

- HTTP 413 独立映射 `RequestBodyTooLarge`，没有普通网络重试建议；不从任意错误文案猜容量。
- 模型客户端增加普通 `requestBodyBytes` 接口，使用与发送相同的 Chat/Responses 序列化器，包括图片准备和 JSON 编码，不发网络请求。路由复用刚才实际使用的客户端，不额外获取凭据；桌面账号包装透传。未知传输返回 0，不假定未知体积为零。
- Runner 仅在明确 413 后启用字节恢复；新请求实际字节数必须严格小于被拒请求，最多四次恢复，不重跑已经执行的工具。
- 压缩同时满足 token 与字节容量，半量是整理软目标，硬上界只要求严格缩小；保护尾部超过半量时仍允许有效改善。原图片路径和原文保留在数据库，只在成功检查点边界调整模型上下文。
- 摘要自身及格式重试也检查编码字节。摘要 413 后从原字段重新分块，按固定指令/原摘要之外的来源部分缩减，最多四次恢复；失败的部分摘要不推进检查点。输出 token 额度保持原值。
- 无法安全缩减的当前内容或未知字节计量停止重试，并明确提示保留原史、换新会话或缩小当前图片。

## 定点证据

验证文件位于 `.cache/request-body-recovery-20261123/`。Windows 11、MSVC 14.44，真实 Core 和正常 App 链接库；测试网络仅本机回环，使用显式测试凭据，无计费调用。

原业务 RED：Chat/Responses 均没有 typed 413；真实 Agent 遇到大请求只调用一次模型即结束，没有恢复。四项断言失败。

修复后定点用例通过：两协议实际请求字节与回环接收字节一致；路由计量不重新读取凭据；旧图请求第二次成功，20 条原始图片记录仍在；保护当前四图的近限会话恢复；无法缩减的当前原文只调用一次，原文保留；摘要自身两次 413 后分块成功，所有尝试输出上限均为 4096。

本轮评审补齐了“摘要仍可能超限”和“把半量错误当硬限制”两个 P2，修正后定点复核未发现新增 P1/P2。

八套 Core 回归已运行：图片上下文、Compactor、ToolLoop、TurnRunner、InputQueue、Runtime、Store 七套通过。ModelClient 套中两条 TCP 连接复用端口相同断言失败；用改动前 Chat/Responses 源文件单独链接相同测试，仍得到完全相同的两条失败，保留 `baseline-transport-run.log`，不冒称全套通过或改断言。新 413 回环与路由验证通过。

正常 App 已完成新 ABI 依赖重编、链接、部署及 PE 检查；最终打包以重新冻结的源码为准。Mac 后续使用同源验证与出包，不把 Windows 回归称为 Mac 实机验收；本任务未替换或重启用户现装。
