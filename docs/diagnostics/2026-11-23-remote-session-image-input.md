# 远程会话输入框粘贴、拖入图片无反应

## 用户操作与预期

2026-11-23，用户明确场景：同账号 A 为 Mac，B 为 Windows；A 打开 B 所属的会话，主要是粘贴或拖入图片没有反应，并非已证实的上传失败。预期图片进入待发送附件，允许只有图片的消息，发送继续走原有跨设备附件上传与所属端接收流程。

## 根因证据

共享桌面组件 `RemoteAgentPanel` 调用 `ComposerTextEdit::setMimeHandler` 时，原回调只有 `mime->hasImage() || mime->hasUrls()`。该接口的 true 表示业务已消费 MIME，`ComposerTextEdit::insertFromMimeData` 随即返回；原回调没有保存图片、收集文件或更新附件，因此内容被静默丢弃。

这段代码同时存在于公开 3.1.3 源码 `266480465a6476985cb5b837dc35ea69274c9439`。选文件按钮原本已有附件接收代码；用户后续澄清以粘贴/拖放为主，本次不声称复现 Mac 原生选文件对话框故障。

## 修改

- 原始图片 MIME 保存为自有 PNG，图片 MIME 与本地文件 URL 接入附件列表。文件选择、粘贴和拖放复用同一校验、去重、数量限制和显示逻辑。
- 仍使用既有 `local_files` 发送、上传及接收协议，未另建图像传输通道。
- 无原文件的图片存放在 outbox 同目录的 `remote-composer-images/`，使用独立 UUID、原子写入和仅所有者读写权限。不能随发送或关闭面板删除，因为持久草稿和未知回执重试可能仍引用图片。
- 附件草稿及时保存；显式清除同步清空持久引用，避免重开恢复已清除的附件。未实现对已保留自有 PNG 的自动垃圾回收；原始选择文件不会被删除。

## 验证

验证目录 `.cache/remote-composer-images-20261123/`。Windows 11、Qt 6.12.0、MSVC 14.44；私有候选基于 `26648046`，包含前一项队列开始通知修复及本次远程输入框差异，不包含 Root 其他 WIP。

原逻辑三个业务 RED：图片 MIME 后发送按钮仍禁用；文件拖入后的 `local_files` 为 0、预期 1；重开草稿后的图片引用为 0、预期 1。原日志保留。

修复后正常 App 构建、部署及 PE 依赖检查通过。相同正常 App 库链接真实 `RemoteAgentPanel`，测试 7 passed / 0 failed（五项业务用例加 init/cleanup，1.035s）：

1. 原始图片 MIME 成为可读 PNG，并允许无文字发送。
2. 本地文件拖入保留附带文字，重复同一路径不重复添加。
3. 图片草稿关闭、重开后仍可发送。
4. 清除图片后重开不恢复旧附件。
5. 一次拖入 12 个文件只接收既定 10 项。

已亲看最终截图 `final-composer.png`：待发送附件显示 1 项，发送按钮可用。测试直接投递自有 MIME 到真实控件，未读写系统剪贴板、未读取用户图片、未发真实模型或供应商请求。

普通回归入口新增为 `remote_composer_attachment_test`，代码位于 `MaiChat/desktop/tests/RemoteComposerAttachmentTest.cpp`；本次实际运行的是同源独立测试工程，链接正常 App 库。
