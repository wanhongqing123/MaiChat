# 每个工具结束后消费补充消息

2026-11-06；main / 9459e7ec 加现有工作区修改。

用户操作：在创作中心向本地或远端 Session 发送任务；模型一次回复要求调用 A、B、C。
在 A 执行期间继续发送补充消息，要求调整后续操作。预期 A 正常结束后立即把已收到的
补充和 A 的真实结果交给模型，由模型重新决定 B、C 是否还需要执行。
尚未开始的旧调用不得先执行，也不能被记录为成功；没有补充消息时保持原执行顺序。

最小复现使用实际 MaiAgent 与受控的进程内假模型：第一轮返回三个工具调用，A 阻塞在
可观察闸门；排队两条用户消息后释放 A，检查第二次模型请求和 B、C 的实际执行计数。
额外检查流式回复期间已经到达的输入、工具失败、审批、停止、原收据去重和重新规划。
不调用付费模型，不停止或替换用户正在运行的应用。

调用链已确认：MaiTurnRunner::runUnchecked 先完整执行 executeTools(calls)，
下一次循环才调用 advanceSteering；executeTools 内没有补充输入检查。
MaiContextBuilder 从持久化工具片段重建调用及结果，Canceled 状态也会回灌。
因此修改位置在共用 C++ 工具循环：单个工具边界发现输入后，给尚未执行的调用补上
明确的“因新输入未执行，请重新判断”回执，保持每个 callId 有对应结果，再消费输入。

验收目录：`/private/tmp/maichat-per-tool-input-20261106/`；其中 before/ 和 baseline.json
保存本次修改前的精确源码。

## 定位与修复验证

修改前将新增用例链接到正在交付的同一份生产 Core 静态库，退出码为 1，27 个断言失败。
可观察到 B 确实执行、C 连同后来模型重新选择的 C 共执行两次；已接受的补充直到整批
结束才进入模型请求。证据 `baseline-red.txt`，不是根据 UI 工具摘要推测。

共用工具循环现在在每个工具启动前检查待消费输入，在等待审批后、真正执行前再次检查。
当前工具正常运行到结束；发现补充后锁定本批不再执行后续项，沿用 Canceled 状态保存
原 callId，输出明确写明 not executed because new user input arrived，并要求模型重评。
这些记录没有调用工具实现，也不触发剩余项审批；已有工具的真实成功或失败结果保留。
模型下一次请求拿到完整配对的调用结果，随后是已接受的新用户消息，按接收顺序排列。
同批旧调用不会在之后自动恢复，只有模型结合新消息重新发出的调用才会执行。

新增用例和原队列用例全部通过（`per-tool-green.txt` / `MaiInputQueueTests.log`）：

- A 等待期间收到两条补充，A 执行一次、B 不执行、模型重选的 C 仅执行一次。
  同时覆盖普通 enqueue、精确绑定的 steer 和 SQLite 中 A 失败的路径。
- 逐一核对下一次模型请求中的原 A/B/C callId、三个相邻回执、两条用户消息顺序，
  并检查实际历史中的 Completed/Error、Canceled、Canceled、Completed 状态。
- 没有新输入时 A、B、C 均按原计划执行；流式模型回复期间已收到新消息时，
  三个尚未开始的旧调用均不执行，三个未执行回执仍配对齐全。
- 审批等待期间收到新输入，即使旧工具随后获批也不再执行；主动 Stop 则暂停保留
  新输入且不额外请求模型；达到现有迭代硬上限时仍把新输入带入最终状态请求。

链接当前生产 Core 与依赖的八套 C++ 回归全部退出 0，见 `core-results.json`。
DesktopSessionSyncHost/Coordinator/RemoteAgentPanel 的 38 项回归全部通过，
见 `desktop-sync-results.txt`。均使用本地假模型，不调用付费供应商。
