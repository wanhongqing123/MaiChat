# 上下文压缩的信息保留核查

## 问题与范围

用户询问当前上下文压缩是否会丢弃上下文。2026-11-19 对 `7d3fd35ffebe12e8e8d91c7325bad04919eb97ad` 的 Runner、Compactor、Builder、SQLite 和原史查询进行只读源码核查，区分数据库原始记录与实际模型输入。未读取用户数据库、调用模型或操作设备；没有据此判断某个现场会话已经发生了语义遗漏。

## 确定行为

1. **原始聊天不因压缩删除。** `MaiSqliteStore::advanceContextCheckpoint` 只持久化独立检查点；消息和片段仍按原表查询。界面历史与原史工具读取原始记录，不用摘要替换聊天气泡。
2. **旧原文会从后续请求中被摘要替代。** `MaiContextCompactor.cpp:661` 起验证检查点、摘要格式和源指纹，再组装摘要与尚未覆盖的原文尾部。检查点失效时从原始历史重新构造。
3. **触发与保留边界有预算限制。** 默认超过扣除生成/工具余量后的输入容量 80% 时尝试整理，以 60% 为目标。通常保留最近两轮；尾部太大时缩到最近一轮，再尝试总结当前轮已完成的较早工具组。当前用户原文和受保护的近期观察保持；Pending/Running 调用不会被伪装成完成。见 `MaiContextCompactor.h:41`、`.cpp:199`、`:227`、`:690`、`:720`。
4. **摘要是有损的语义记录。** 六类内容为目标、约束、决策、进展、未决问题和来源说明；每批把旧摘要与新增来源合并。摘要预算至多约 8192 token（小窗口更低）。`validateSummary` 只证明格式及非空合法，不验证所有原事实和约束逐条覆盖，因此可能遗漏细节，多次合并也不能保证无损。见 `.cpp:65`、`:103`、`:471`、`:780`、`:914`。
5. **回查能力不等于每次已回查。** `session_history` 可按本会话消息/片段精确读取文字和工具输入输出，并分页检索。摘要提示模型按需回查，宿主不会自动把全部被压缩原文重新发送。引用索引也只按预算展示部分条目，并标明 `has_more`。见 `MaiSessionTools.cpp:98`、`MaiContextCompactor.cpp:135`。
6. **失败并非一律保留全文继续。** 格式/大小修正共用最多两次尝试。Protocol 摘要失败且原请求仍适配时，延期压缩并使用原请求；硬超限时，只有实际可回查原史的请求才允许部分来源索引恢复。索引放不下时可能省略早期用户正文，仅保留有界来源元数据；必要尾部也放不下则报错。网络、取消、限流、存储和来源冲突不按此路径恢复。数据库原文不随降级删除。见 `.cpp:350`、`:578`、`:763`、`:823`、`:882`。

## 与压缩独立的输入筛选

Builder 默认没有固定字节预算裁剪历史文字；非零预算属于显式有损选项。历史思考草稿默认不回传，旧图片像素也不会每轮全量重发；当前用户新图片、近期工具图片和有界附件引用按独立策略保留。引用消息正文预览有 4000 字节边界。上述只影响请求副本，不能据此说模型永远持有旧图片或完整引用原文。见 `MaiContextBuilder.h:22`、`.cpp:104`、`:179`、`:200`、`:380`。

## 核查边界

一个静态反例是：原文包含特定文件名、数字或用户限制，摘要仅返回 `goals:["Continue"]`、其余五数组为空，仍符合格式校验。其他容量/来源/存储检查满足时，该合法摘要不会因缺少原事实被自动拒绝。此例用于说明现有校验能力，没有新运行模型或把它写成某个现场摘要的事实。

既有 `MaiContextCompactorTests.cpp:1444` 起的测试逐字核摘要输入来源完整，并明确允许摘要不含原 URL、由独立引用保留；`:1583` 起验证增量任务使用旧摘要而不重发已覆盖原文；`:3138` 起覆盖部分元数据索引及原文按 ID 回查。这些源码断言支持“原史可追溯”，不能证明摘要语义无损，本轮没有重复执行这些测试。

与已安装 230 对应的产品源码 `f785e2c2` 比较，Compactor/Runner 后继改动仅是会话路由身份透传和一致性校验；Builder 和原史读取在该区间无改动。这里说明现有实现，不代替设备当前进程、特定会话检查点或摘要质量的实测。未修改产品策略，也未进行付费重现。

结论：聊天记录可追溯，但模型当前窗口不是旧对话的无损副本；应明确承认摘要遗漏和未主动回查导致忘记细节的风险。

## 当前压缩阈值及官方容量

后续问题要求核对各型号约 1M 窗口与何时开始压缩。已重新核对 [DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/)、[GLM-5.3](https://docs.bigmodel.cn/cn/guide/models/text/glm-5.3)、[GLM-5.3-Flash](https://docs.bigmodel.cn/cn/guide/models/vlm/glm-5.3-flash) 和 [Fable 5.2](https://openrouter.ai/anthropic/claude-fable-5.2) 当前官方页面：约 1M 容量与现目录一致。

App 云端请求的 `maxOutputTokens` 默认为 0，未覆写目录的 `defaultOutputReserveTokens`，因此本地预算采用官方最大输出作预留；这不会将该数字发成生成上限，也不表示每次实际生成或收取这么多输出。默认带工具时另预留 8192 token，开始整理的门槛是 `floor((window-outputReserve-toolReserve)/100)*80`。

| 型号 | 目录窗口 | 本地输出预留 | 开始尝试整理的输入估计阈值 |
| --- | ---: | ---: | ---: |
| DeepSeek Flash / V4 Pro | 1,048,576 | 393,216 | 超过 517,680 |
| GLM-5.3 / Flash | 1,048,576 | 131,072 | 超过 727,440 |
| Fable 5.2 | 1,000,000 | 128,000 | 超过 691,040 |
| Particle-1 Free | 1,048,576 | 131,072 | 超过 727,440 |

这些是一次请求的上下文输入估计，包括固定指令、工具声明、历史、回传状态及图片余量，不是字符数或多次账单用量之和。默认估算并非各厂商 tokenizer 精确值；同一 Runner 若真实 input usage 高于估算，会提高倍率并更早触发。软区延期等情形另有边界，越过阈值不代表摘要一定已成功。

- [ModelInfo 的通用阈值](https://github.com/openai/codex/blob/6271f35f527bf7709b9af5e4e752e9f122706a17/codex-rs/protocol/src/openai_models.rs#L577)：自动压缩默认直接取原窗口 90%，有显式型号阈值时取更小者；可用窗口默认 95% 是另一项计算，不能相乘成 85.5%。没有 MaiChat 的“先扣最大输出再乘 80%”链。具体型号/配置仍可能更早，不能把 90% 承诺给所有现装会话。
