# 上下文压缩：要求原文保护与可见状态

时间：2026-11-21，Windows x64。基线 `d60ad0ee8513180a86d681c0881c0ca7a8f36ab9`。用户反馈为“压缩后忘记要求或关键细节”和“状态不透明，不知道何时压缩”。本次未读取用户聊天或调用真实供应商；下述复现均使用本地自造历史及固定模型。

## 原有逻辑与证据

1. Runner 构造请求，Compactor 按实际型号窗口及本地计数/估算判断容量。默认原窗口 90% 触发、95% 为输入硬预算，明确的输出预留还会收紧预算。
2. 较早的已完成轮次被模型逐块汇总为 goals、constraints、decisions、progress、open_questions、source_notes 六个数组。近期一至两轮和受保护工具观察保留原文。
3. 格式校验要求六数组结构正确、条目非空、至少有一项内容，但不能证明某条用户要求没有被漏写。下一批又在 previous_summary 基础上合并，因此遗漏可继续传播。
4. 正常摘要独立索引优先保护链接、路径和来源，不等于保护全部旧用户要求。原史仍在 DB，只说明可回查，不表示仍在后续主模型输入里。
5. reused/advanced/deferred 原先只在 Runner 内部消费；桌面原有 contextSize 是隐藏的已加载字数标签，既不是窗口占用，也不显示整理进度。

本地 Codex `553c764e8b99fa519e9c6eb9b657875ef0f5e1c1` 的 `core/src/compact.rs` 保留有界原用户文本，`session/context_window.rs` 区分容量口径。借鉴这些边界，不复制其特定远端压缩服务或增加新依赖。

## 实际复现

- 固定摘要返回合法六数组，但故意省略 `OWNED_REQUIREMENT_ALPHA: never publish the draft; keep the exact label cobalt.`。
- 原实现压缩后及复用检查点后的请求不再包含这条原文，状态回调也不存在。`MaiContextCompactorTests --retained-requirements` 实际 RED 10。
- 后续用例增加第二次压缩及 label 改为 azure 的纠正；同时检查原禁止发布要求与新纠正都仍在最终请求，不只检查检查点格式。
- 元数据优化的新增失败夹具也实际 RED 3：逆序恢复时 Memory 应与 SQLite 同样按 ID 选择最新消息；终态写失败后即使旧 Running 元数据可读，普通查询也必须优先报告存储错误。
- 占用展示口径用例实际 RED 2：当容量估算已按供应商 usage 提高倍率，状态数值也须使用同一校正，不能显示较低的未校正数字。
- 终态通知缺失的 UI 用例实际 RED 1：已观察到轮次错误但最终上下文更新未到达时，旧标签继续显示整理中。修复后，缓存按原始 turnId 收尾；在 active 为空且 B 终态投递中断时，A 的迟到事件也不能关闭 B。

## 修复

### 要求文本独立保留

- 每次组装检查点，从原始历史中单独选择已被摘要覆盖的真实用户文本，写入宿主构造的 original_user_messages；不依赖模型摘要复述。
- 排除导入资料、工具输出、待消费输入和仍在 tail 中的当前用户原文。不改变原消息，不额外赋予历史文本或引用内容权限。
- 优先最初需求与近期纠正，最终按原时序发送。展示预算为窗口 1/8、最多 20000 个所选模型计数/估算 Token，只选完整文本；未纳入部分明确带 included/total/has_more 与原史回查提示。
- 保护层与摘要、指令、工具、媒体及 tail 一起接受完整输入硬预算检查。复用也收紧过大的保护层；真正生成新摘要后重新争取最大原文额度，最终仍按完整预算收紧，防止容量退让永久丢掉本可保留的要求。
- 此层从原始记录重建，旧的合法检查点也可获得保护；不用仅为补这层再调用摘要模型。

### 状态与展示

- 新增纯数据 MaiContextStatus：Preparing、Summarizing、Ready、Deferred、Failed、Interrupted，包含前后输入计数/估算、窗口/有效输入上限、检查点版本、原文保留数量及来源索引恢复标志。
- 展示计数与容量决策使用同一保守校正；它不是累计消费、现金余额或供应商实际计费 Token。
- 状态进入原始轮次的持久记录。内建 Store 只更新元数据，不重写大正文或覆盖并发追加的工具片段；先保存再发布携带快照的事件。
- 普通 getTurnOutcome 与只读 session_status 工具共享事实。专用 readTurnMetadata 不加载 parts，桌面冷切会话也不扫描最近 32 条完整正文。
- 进程重建将遗留准备/摘要阶段修正为 Interrupted，不重发请求。异常收尾的最终轮次事件也带状态，避免界面永远显示整理中。
- Windows 创作中心头部复用标签，显示“正在整理对话…”、“对话整理未完成”或“上次上下文已用约 X%”。提示说明这是上次请求输入的估算，不是实时剩余空间或账单；新的输入/输出在下次准备请求时重算。
- 仅来源索引恢复会在头部直接显示“摘要不完整 · 原史可查”；提示进一步说明有损边界、较早用户文本纳入数量和原史回查。不同会话及迟到轮次事件隔离。
- TokenEstimate 单独放在轻量数据头；消息/状态模型不因显示容量而依赖模型客户端接口。

## 边界

- 有限窗口不能逐字承载任意长历史；保护层占用输入预算，未纳入的原文仍需回查。这不是语义无损或模型绝不遗忘的保证，也未作真实供应商记忆效果评测。
- 新材料仍有上下文输入成本；未改变默认型号、输出上限、effort、缓存/路由价格守卫、权限或工具执行策略，未新增真实模型请求验收。
- 本批状态展示实测为 Windows 生产组件。macOS/iOS/Android 本轮没有构建/运行，移动端用户界面没有本次标签接入；共享 Core 修复也需在对应端同源重编后才进入其 App。
