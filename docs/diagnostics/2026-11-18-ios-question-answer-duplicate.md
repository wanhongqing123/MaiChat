# iOS remote question answer appears twice

2026-11-18, source baseline `223bdb08ac69616a3020ee0cf8b403b8dd9fc0d6`.

Reproduction: open Creation Center in an owned remote question conversation, answer with the ordinary composer, accept the tuple-bound owner ACK, then publish the completed question part through the production remote history decoder. Expected: one answer before/after refresh, with the same sender appearance used for queued messages and history. Two deliberate equal-text sends remain two messages.

The owner correctly returns `question_id`, rather than inventing a user-message ID. The iOS outbox previously searched only `messages.id == acceptedMessageID`. Once terminal question history removed the temporary answer echo, its accepted queue entry resurfaced as a second blue delivered row while the terminal question rendered the gray answer. The screenshot alone did not establish a duplicate server row or a second execution.

The fix uses one owner/conversation-scoped canonical-history predicate for display and durable retirement. Normal sends still match their canonical message ID. Answers additionally require matching accepted question ID, answer binding, captured question ID and exact part identity; captured message/source-session identities are checked when supplied. Completed question parts from normal history, projected child questions and root updates can retire their accepted entry. Missing legacy identity is retained rather than guessed from text. Echo cleanup uses the same question identity. Outbox, canonical user text and question answers now share one sender bubble modifier; queue status stays outside it.

Native iOS Simulator verification (iPhone 17 Pro, iOS 26.5, isolated review bundle; no user database/model request): baseline ordinary remote UI reproduced 2 matching answer texts instead of 1 (`red3.xcresult`, 11.434 s). Fix: remote canonical refresh, local normal-composer question and five FIFO sends including two identical texts passed 3/0 in 52.647 s. Final fixture additionally closes the keyboard through the ordinary input-mode button and refreshes the same canonical page twice: 1/0 in 12.974 s. Screenshots of queued equal-text messages and the final single remote answer were inspected. The first fixture build failed due to attempting to mutate a let parts array; that fixture error was corrected before the baseline runtime failure and is retained in the logs.

Evidence: `/private/tmp/maichat-ios-question-echo-20261118/` contains input commands, build/test logs, xcresults and owned screenshots. Debug seams replace only peer transport; production queue, answer binding, owner tuple/ACK validation and remote history projection run normally. No real remote account, phone installation, server deployment or existing app replacement was performed in this scope. The installed phone remains the previously verified 3.0.1(227); this source change is not yet installed there.

## Pending-only source message boundary (R2)

Independent review identified a display-only boundary: a question whose owner message has not arrived uses `question-pending-<qid>` with `questionProjection=true`, the captured source session and original part ID. R1's strict real-message match suppressed its accepted echo. The owned remote fixture now starts with questions but an empty root messages page. This first exposed a pre-existing view guard that rendered `visibleMessages` only when root `messages` was nonempty. The list now derives rendering, empty state and scrolling from the same projected display rows. With that guard corrected, the accepted-answer regression reproduced an exact 0 rows versus 1 failure in 15.337 s. The display echo now narrowly recognizes that exact pending projection and its session/part; canonical retirement remains bound to the real owner-message identity. Both pending-only and owner-present remote cases passed 2/0 in 26.140 s, including subsequent canonical arrival and replay. R2 keeps the R1 color and receipt rules; it adds no text matching or new transport.
