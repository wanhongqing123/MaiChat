# 摘要失败造成非必要暂停：本轮恢复边界

## 需求和已复现路径

用户强调模型交互中的暂停影响任务体验。本轮基线为
`20db4175206b713a167abbd3c1894b47d14e3b8a`，不读取现场数据库、不请求真实供应商。

复现使用自有临时历史、已落库工具结果及隔离模型：上下文超过预整理阈值、但仍在扣除
生成和工具余量后的输入预算内；摘要连续返回两次坏格式。原路径在摘要失败后直接结束
Runner 并发 SessionError，即使同一份原请求仍可发送。历史及已有工具结果保留，但没有
可以恢复的旧 Runner；发送回执重试不等于恢复该任务。

预期：这类整理失败不结束当前轮，继续使用完整原请求或有效旧检查点；不采用半摘要、
不重置工具循环、不主动重放已执行工具。同轮后续请求暂缓非必要整理，每次仍重新核对
模型容量、供应商 usage 校正倍率及预留。真正超过预算时必须再整理或如实失败。

## 选择与边界

采用原请求仍适配时暂缓整理的方案；保留现有一次格式修正。不以删原文、局部摘要或
确定性裁剪替代失败的摘要，也不增加全局重试或无限循环。

只允许摘要生成/flush 的 Protocol 失败走此分支。取消、Network、RateLimited、已有存储
写入失败、检查点 CAS/源变更及真实超限保持失败；检查点不得推进。普通 C++ preparation
结果/options 与 Runner 内部标志表达延期，不增加数据库、wire、供应商代理或新 UI 弹窗。
计数为模型已有精确值或明确估计，不将估计冒称供应商实际 token 用量。

## 实施与验证

先仅加入旧 API 可执行的行为用例，在原生产源上运行失败；再做五源窄修并使用同例复核。
必须检查：软区失败后同轮继续、原工具计数/调用身份不被重置、倍率校正后过界不延期、
有效旧检查点和后续 batch 失败时原请求/引用不变，以及取消、网络、存储和 CAS 的拒绝。

### 修复及最终 GREEN

五源修复为 `MaiContextCompactor.cpp/.h`、`MaiTurnRunner.cpp/.h` 与原有
`MaiContextCompactorTests.cpp`。本次没有其他 Core 生产变更。普通 preparation 返回
`deferredCompaction`，Runner 用本轮私有标志暂缓软阈值整理；成功推进检查点清该标志。
每次请求仍用当前倍率与 reserve 检查硬预算，不重置工具循环或调用编号。

fallback 前只读核对摘要开始时完整 store 前缀、实际采用的 source 投影和完整旧检查点。
这同时处理 Runner 有意过滤未消费 steering 的情况；原来源改变返回 Busy。只追加尚未
采用的后缀允许，后缀不混入已计预算的原请求；不靠写入或 CAS 伪造一次成功压缩。

最终定点用例验证：

- 软区同一 Runner：主请求 3 次，摘要请求 2 次，两项工具各执行一次，最终回答落库。
- usage 倍率升为 1.25 后：主请求 2 次、摘要请求 4 次，两项工具各一次，超硬预算失败。
- 硬区成功整理后继续同一 Runner，新请求估计 5526，重新超过 5280 的软阈值且小于
  6656 的硬预算；再次整理发生，证明推进检查点后已恢复正常软阈值策略。
- 后续 batch 失败保留完整旧检查点、引用与原请求；取消、网络、限流保持原错误，已有
  写入错误为 Internal，Protocol 同时发生来源或检查点变化为 Busy。坏摘要未被发送或保存。
