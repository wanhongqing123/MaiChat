# smoothing 与“面膜感”报告：已确认事实与待验证假设

2026-11-05；main / eee43402 与当前 v8 工作区。只做诊断说明，不修改美颜算法，
不以补充红润功能代替同一原图的根因验收。

## 参数与实际路径

当前 schema 确实没有独立 redness/rosy。warmth 是有界 RGB 红蓝平衡，brightening
是局部增益，两者与专门红润控件的定义不同。FaceUnity 官方也分别提供磨皮、美白、
红润参数，但参数独立存在本身不能证明“缺红润必然导致面膜感”。

普通 smoothing 在 `MaiPortraitEngine::skinColor` 中实际执行
`cv::bilateralFilter(rgb, blurred, 7, 22, 5)`；合成权重是
`smoothing × 0.65 × mask/255`。不是固定极小系数，也不是未启用双边滤波；固定
滤波尺度、值域阈值、遮罩覆盖与原图分辨率是否适合该图，仍需原样本复核。
身体专用净肤还包含独立引导/纹理保留阶段，脸部因五官保护不直接复用去毛通道。

## 指标不能直接推出的结论

- 美颜 changed_pixel_count 统计任一 RGB 通道发生变化；比较工具
  changed_pixel_fraction 使用灰度差阈值，默认 `changedPixelThreshold=16`。
  两者同时出现 58394 与 0 不矛盾；需保留实际阈值、预处理与输出元数据。
- 全图 Laplacian 方差会混入背景、头发、衣服和五官；报告中皮肤覆盖仅 12.5%，
  不能据全图下降 0.8% 直接判定皮肤滤波无效。需要固定同一 mask 内区，避免把
  mask 边界作为纹理，分别比较皮肤高频、五官、背景与实际差分幅度。
- 按提供的同一亮度口径，P90−P10 从 146−37=109 到 153−37=116，区间增大。
  这既不能证明局部微对比被压缩，也不能代替局部对比度测量；分位数不等同于
  对同一批像素逐一跟踪。原图和当前工具运行版本尚未到手，未宣称复现 −0.8%。

## 后续同图实验

需要原图、smoothing 0/0.5/1 与 whitening 对照输出、原始灰度 mask、完整工具调用
及返回 JSON、指标脚本（ROI、阈值、色彩与尺寸预处理）、本地自然版及处理脚本。
参数需能看出是否启用个人模型和身体 AUTO，不能从“其余数值为零”推断所有开关。

优先区分：滤波尺度/值域保护、皮肤内区实际变化、LUT 的 L*/a*/b* 与色度变化、
遮罩边界内外的色差和亮度梯度。当前美白颜色策略允许把色度缩小到输入与 LUT
目标的较小值，这也是应独立验证的候选因素，不等于已经定位了面膜感根因。

频率分离应区分 tone 与 texture；若将全部高频原样叠回，毛孔和瑕疵也会叠回。
固定给 a* 加常量只能改平均色调，不能恢复已经丢失的空间红色差异或纹理。
因此红润可作为独立产品能力讨论，算法修复需先证明实际损失发生在哪一层。
