# 压缩要求保留与可见状态

用户明确反馈：压缩后忘记要求/细节，以及不知道何时压缩。本批沿此前已授权的 Core 架构补齐继续，不读取真实聊天或调用付费模型。

## 已核机制

正常成功摘要只有模型生成的六数组和独立链接/路径索引；格式合法不代表约束完整。保留最近原文不能保护更早的全部要求。后续又把 previous_summary 合入新摘要，遗漏会累积。原史数据库仍在，但不等于已在模型输入中。压缩标志目前只被 Runner 内部消费。

## 方案

1. 从检查点覆盖的真实用户原记录，每次重建独立原文保护层，跳过导入资料、工具、待消费输入以及仍在 tail 的当前用户。优先最初需求和近期纠正，最后按原时序输出。不依赖摘要模型选择或复述这些内容。
2. 原文展示预算按模型窗口 1/8、最多 20000 tokens；只选完整消息，不截断要求伪称完整。整体请求仍受原硬预算约束；必要时收紧展示预算，并公开纳入/总条数和回查提示。原数据库不变，不能承诺任意长历史语义无损。
3. 普通 Compactor 提供准备、摘要中、就绪、延后、失败、中断状态，带输入估算/是否精确、有效上限、检查点版本与原文保留数量。
4. Runner 将该状态连到已持久化的原始轮次记录，先保存再发事件；普通 API/模型状态工具读同一事实。状态不包含原文/摘要/思考。
5. 桌面复用现有头部状态标签与事件桥，显示整理中和上次请求估算，tooltip 说明有损摘要/原史回查及保留条数。切换会话隔离，失败不冒报完成；未获得的窗口/估算不显示假 0%。其他端共享 Core 事实，按用户指定平台继续核对。

## 验证

- 固定模型返回格式合法但故意省略约束的摘要，检查第一次压缩和复用后原要求仍在最终请求。
- 网络失败不推进检查点，观察确实发出失败状态；窗口/取消/CAS/原史及原工具单执行回归。
- 用户原文在预算外必须说明部分保留，不挤掉当前输入；导入/工具文本不能晋升用户要求。
- 普通桌面组件自造夹具展示整理中/完成/失败、切会话隔离并截本地组件图，不动现装用户配置。
- 构建全 ABI 相关消费者，Core 回归、控制台 e2e 与目标 UI 窄用例。记录未验证平台，不自动发布或换现装。
